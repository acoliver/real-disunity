# Playing the original games

`worldrunner-play` runs Snake, Pong or Breakout from its original Unity scene in a window. It fetches the game with `worldrunner-original-games`, plans the scene with `unity-import`, compiles the game's scripts unchanged with `csharp/OriginalGames`, and loads the scene through the `csharp/Disunity.Play` bridge. Each frame advances the world and draws its presentation in the desktop host from `worldrunner-scene-viewer`.

## Command line

```sh
cargo build -p worldrunner-disunity-ffi
cargo run -p worldrunner-play -- pong
cargo run -p worldrunner-play -- breakout --frames 300 --fixed-dt 20 --key 30:a:down --key 90:a:up --capture 120:breakout.png
```

| Option | Meaning |
| --- | --- |
| `--size WxH` | Window size in pixels; 960x540 by default. |
| `--frames N` | Close the window after N frames. Without it the game runs until the window is closed. |
| `--fixed-dt MS` | Advance every frame by MS milliseconds instead of the measured frame time. |
| `--key FRAME:KEY:down\|up` | Press or release a key before frame FRAME. Keys are lowercase names: letters, digits, `f1` to `f12`, `space`, `enter`, `escape`, `backspace`, `tab`, `delete`, `insert`, `home`, `end`, `pageup`, `pagedown`, `arrowup`, `arrowdown`, `arrowleft`, `arrowright`, `shift`, `control` and `alt` (the left keys), `capslock`, `numlock`, `scrolllock`, `pause` and the punctuation keys. They reach the game as the standard `KeyCode` values. |
| `--capture FRAME:FILE` | Write frame FRAME as it was presented to an RGB PNG. |
| `--seed N` | Seed the game's `Random` before the scene loads, so runs with `--fixed-dt` and the same keys repeat exactly. Without it, as in Unity, each run differs. |
| `--font FILE` | The TrueType file to use for Unity's built-in Arial. On Linux the default is the font `fc-match Arial` selects, usually Liberation Sans, whose metrics match Arial. |

Keyboard input from the window works the same way as scheduled keys. Pong's left paddle uses W and S, and Breakout's paddle uses A and D.

The engine library is found through `DISUNITY_FFI_LIBRARY` or beside the `play` executable, where `cargo build -p worldrunner-disunity-ffi` puts it. Builds go to `target/play/<game>`. The command needs the .NET 8 SDK and system Git, and network access the first time a game is fetched.

Settings the engine does not reproduce and input axes it cannot deliver are printed when the scene loads. Snake is steered with W, A, S and D.

## Built Unity players

`play --player <data directory>` starts a scene of a built Unity player, the `<Game>_Data` directory beside its executable, without a window:

```sh
cargo run -p worldrunner-play -- --player /path/to/Game_Data --scene level0 --frames 60
```

It writes the script layouts of the player's game assemblies with `csharp/Disunity.Layouts`, plans the scene file with `unity-import`'s `plan_player_scene`, and boots the same `Disunity.Play` bridge. The bridge resolves the player's assemblies in its load context, runs the player's startup hooks in Unity's phase order around the scene, loads the scene's plan and the host advances `--frames` frames (one by default) of `--fixed-dt` milliseconds (1/60 s by default). `--scene` names the scene file, `level0` by default. Each `--arg VALUE` (repeatable; each value is one argument, in order) is part of the player's command line: `Environment.GetCommandLineArgs()` returns the player's executable path first, then the `--arg` values, for example `--arg game.zip --arg -headless` for a game that loads the save named on its command line. The executable path is the engine's choice: the data directory's parent joined with the data directory's name without its `_Data` suffix, plus `.exe` for a Windows player. The run logs it as `command line: ...`. Each step prints a `[player]` line, along with what the plan or the loader leaves out, so the last line before an error is the step that failed, and the error names the hook, component or frame. Builds go to `target/play/player`, and game assemblies that give native code delegates for `[MonoPInvokeCallback]` static methods are rewritten into `target/play/player/callback-cache` so those delegates stay callable (see `docs/csharp-games.md`). A player that imports a native library it does not ship for this platform, such as Old World's Wwise `AkSoundEngine`, loads its own `Plugins` file when there is one and otherwise the engine's substitute from the engine library's directory (the silent Wwise library, which `--player` builds there). See "Player native plugins" in `docs/unity-projects.md`.

## Offscreen work from a player

`worldrunner_play::offscreen` maps the offscreen work a player's scripts record in the world (camera renders into render textures, `Graphics.Blit` and `Graphics.CopyTexture`) onto `worldrunner-render-program`'s `OffscreenFrame`, so the player's own shaders draw it. It is in `play` because it needs the world's types (`world-simulation`), the importer's readers for the player's serialized files (`unity-import`, a Tool crate) and render-program; `scene-viewer`, the one Host crate, may not depend on the importer.

| Piece | What it does |
| --- | --- |
| `GraphicsSnapshot` | `worldrunner_world_simulation::graphics::GraphicsSnapshot` holds what the frame's records reach: the cameras they name with their pose, the renderers those cameras may draw (every layer a camera's mask admits, not only the screen camera's), the materials and shaders of those renderers and of the blits, the render textures with their samplers, the global state, and the compute shaders and buffers the dispatches name. `DisunityHost::graphics_snapshot()` drains it once per call, and `GpuFlush::snapshot()` does the same inside a flush; a frame with no work gives an empty snapshot. |
| `OffscreenAdapter::adapt` | Loads each shader (`ShaderLoader`, or any `ShaderSupply`), uploads the meshes and stored textures the frame names through `Assets` (implemented for `DisunityHost`), and maps the snapshot with `adapt`. A mesh keeps its vertex channels under the numbers the host stored them with (0 position, 1 normal, 2 tangent, 3 colour, 4 to 11 texture coordinate sets 0 to 7; blend weights and indices are left out), each as 1 to 4 floats, and its ranges become the sub-meshes by range number; a range that draws and is not triangles refuses the mesh by the name of its topology (`QuadTopology`, `LineTopology`, `LineStripTopology`, `PointTopology`). A stored texture is uploaded with its wrap along u and v and its filter as render-program's `SamplerState`; a render texture brings the same from its `WorldSampler` wherever a property names it. Mirror once is read as mirror; the wrap along w, anisotropy and mip bias are not carried, and a render texture read as the source of a blit or a copy is read with the fixed sampler. A blit of every pass (-1) becomes one record for each pass of the material's shader, in order. A record that names a destroyed texture, camera or material, or something the host cannot supply, is skipped and counted by reason in the `Report`. A dispatch is not a frame record: `Adapted::dispatches` says how many records come before it, and the render textures its properties name are in the frame. |
| Mesh draws (`OffscreenWork::DrawMesh`) | A command buffer's mesh draw is drawn like one renderer of a renderer list with one sub-mesh, into the render target bound at its place in the frame (`SetRenderTarget`, an optional `ClearRenderTarget`) with the view and projection of the last `SetViewProjection` or camera setup. The host reads the mesh by the record's identity through `Assets`, as it reads a renderer's mesh, and the draw takes the mesh's channels, the material's constants and textures, the shader pass by index and the render state of the pass as a list draw does. The record's matrix is the object's `unity_ObjectToWorld` (and its inverse `unity_WorldToObject`); `unity_MatrixV`, `unity_MatrixVP` and `_WorldSpaceCameraPos` come from the view, and are missing before any view is set. The sub-mesh number is the mesh's range number. A `pass` of -1 draws every pass of the material's shader in order inside one draw, so a later pass blends over an earlier one; any other pass draws that one. A mesh draw is left out and counted in `Report::skipped` (and `skipped_by_kind` as `DrawMesh: <reason>`) as `MeshUnavailable` (the store does not hold the mesh, or it failed to upload), `EmptyMesh` (the mesh has nothing to draw, which also adds the `mesh with nothing to draw` census line when the mesh is read, or the sub-mesh has no indices), `NoSuchSubmesh` (the sub-mesh number is past the mesh's ranges), `NoSuchPass` (the pass is past the shader's passes), `UnboundTarget`, `PartialViewport`, `StaleMaterial` or `ShaderUnavailable`. |
| `build` | `OffscreenState::build` for the adapted frame. When the state refuses the frame, each render texture and then each record is built alone, the ones refused are left out and counted by the error's name, and the rest are built together. |
| `ShaderLoader` | Opens the serialized file a `ShaderSource` names under the data directory (a path that leaves it is refused), decodes the shader object, takes the chunks of its Vulkan platform and builds the `ProgramShader`. Sources are cached, failures included. |
| `builtins`, `camera` | The per-draw values (`unity_ObjectToWorld`, `unity_WorldToObject`) and per-camera values (`unity_MatrixV`, `unity_MatrixVP`, `_WorldSpaceCameraPos`). The module documentation gives the evidence for each name, how it is computed, and the names left missing with the number of the player's variants that hold them. |

`play shader-census <player data directory>` loads every shader of a player through the loader and prints counts. All 171 shader objects of the Old World player (Unity 6000.3.15f1) load as programs, with 663 passes. It also prints how many loaded shaders have no pass with a `LightMode` tag and the passes by `LightMode`: in the Windows build's data 147 of the 171 shaders have none, and 603 of the 664 passes have no `LightMode`; `DepthOnly` (9), `SHADOWCASTER` (10), `UniversalForward` (13) and `DepthNormals` (8) are the largest tagged groups, and no pass is tagged `SRPDefaultUnlit`.

`unity-import player-shader-builtins <player data directory>` is the aggregate measurement the built-in names rest on; see [the importer guide](../../docs/unity-projects.md).

Vector arrays and matrix arrays (`PropertyValue::VectorArray` and `MatrixArray`) are carried by name like the single values. An array the global state holds when the frame starts, one a command sets with `OffscreenWork::SetGlobal` and one a dispatch holds is copied into the constant buffer member of its name in element order, each matrix column by column. A command's array applies to the records after it until another command sets that name. A pass that declares fewer elements than the array holds is not drawn: its record is left out and counted as `record:Constant`, with the cause `record:Constant/ArrayTooLong` and the property, the given and the declared counts in the example. A dispatch in that case is left out as `dispatch:Constants`. `DispatchTrace::constants` lists an array by its element count. The same mapping serves the values of a material and of a property block. `tests/global_arrays.rs` (in `offscreen/tests`) checks this on a real adapter with a blit pass that shows one element in each half of its target and a kernel that copies its array constants into a buffer; the matrices it uses have rows that differ from the columns shown, so a transposed matrix changes the result.

### Compute and the GPU flush

`OffscreenHost` is the player's side of a device: the `ProgramRuntime` and its arena (made once), the `OffscreenState`, the `OffscreenAdapter` and a `ComputeAdapter`. `ComputeAdapter` asks a `ComputeSupply` for the `StageProgram` of a kernel, the way `ShaderSupply` gives a shader's passes, and keeps it until the shader's generation rises. A dispatch is prepared by name: the properties pack into the kernel's constant buffers, the textures the properties name bind to the texture parameters the kernel declares (`StageProgram::texture_targets`), and each compute buffer the dispatch binds is uploaded from the contents the snapshot holds and bound to the storage buffer of the same name (`StageProgram::buffer_targets`). A dispatch that cannot run is left out and counted as `dispatch:` and the cause (`StaleShader`, `NoCompiledCode`, `ProgramLayout`, `MissingTexture`, `TextureUnavailable`, `UnboundBuffer`, `StaleBuffer`, `BufferUpload`, `Constants`).

`OffscreenHost::flush` runs a snapshot's work to completion in call order, offscreen records and dispatches alike. Each run of records is built, admitted and encoded into one frame of the runtime's authority, followed by the dispatch after it, and that frame is submitted. A last submission copies every compute buffer a dispatch bound, and the call waits for that submission alone. The buffers whose bytes changed come out as `BufferWrite`s, and `FlushOutcome::apply` hands them to a `BufferSink` (`GpuFlush::write_compute_buffer` in a flush, `World::set_compute_buffer_data` in a test). Each run is its own submission because the buffer the runs' constants share is rewritten for the next run. On an error nothing is written and the managed engine returns the contents the CPU holds.

`tests/flush.rs` (in `offscreen/tests`) runs a synthetic world on a real adapter: a camera clears an R16 float render texture to 0.25 and draws 0.5 over its left half, a kernel multiplies each texel by a constant-buffer vector (2) and writes a storage buffer, and the flush writes back sixteen values of 0.5 and 1.0 that the test predicts from those numbers. A second test puts a dispatch before and one after the camera render and checks that only the second buffer changes.

`PlayerKernels` is the supply `PlayerGpu` uses. A world compute shader's source names a serialized file and the path id of the compute shader object in it. The loader decodes the object with `unity-serialized`'s `ComputeShader`, takes the kernel at the dispatch's index from the SPIR-V platform (renderer 21), runs its variant compiled for no keywords and builds the `StageProgram` with `render_program::compute_kernel::kernel_stage`. A dispatch whose kernel cannot load counts as `dispatch:` and the cause: `Unreadable` for a file or object that does not decode, `NoCompiledCode` for a shader without a SPIR-V platform, `NoSuchKernel`, `NoVariant` for a kernel that has no variant without keywords, and `Program` for a variant the renderer cannot build. `unity-import player-compute-report <player data directory>` counts the same outcomes over a whole player. In the Old World player all 76 of its kernel variants become programs with layouts and targets (before storage images were bound, 10 did and the 66 that write storage textures failed by name). The 66 declare 80 storage images between them, every one write-only: `R32Float` 2D (15), `R32Float` 2D array (4), `R32Uint` 2D (24), `Rg32Float` 2D (17), `Rg32Float` 2D array (4), `Rgba32Float` 2D (2), `Rgba32Float` 3D (6) and `Rgba8Unorm` 2D (8). Each is a format that a device made with no optional features binds as a write-only storage image, so the report counts no variant as needing device features.

A kernel's storage images bind as its buffers do, by name. `StageProgram::image_targets` lists the storage image parameters with their prepared set and binding, and the dispatch's texture properties of those names must be render textures (any other texture is left out as `StorageSource`). Before a flush builds anything, `ComputeAdapter::storage_textures` finds the render textures the snapshot's dispatches bind this way and `OffscreenState::bind_as_storage` marks them: a marked texture is made with storage binding usage when the device binds its format, and a texture that existed without it is made again, empty, the first time it is marked. A texture stays marked, so later flushes keep its contents. `ProgramRuntime::check_storage_images` then checks each binding before the dispatch is recorded, so a texture the kernel cannot be given leaves that dispatch out and not the flush: `StorageFormat` when the device cannot bind the render texture's format as storage, `StorageFormatMismatch` when the texture's format is not the one the kernel declares, `StorageUsage`, `StorageDimension` (the view the kernel declares is not the one the record's shape binds through: a 2D view for a plain texture, a 2D-array view for an array, a cube or a cube array, a 3D view for a volume; the reason names both shapes), `StorageSamples`, `StorageAliased` (one texture bound to a storage image that is written and to another binding of the same dispatch) and `StorageUnsupported` (the kernel declares a format or access the device cannot bind) and `StorageLimit` (the kernel binds more storage images in its stage than the device allows). Two Old World variants bind five storage images, one more than the default limit of four, so the headless player prefers a device with eight where the adapter has them (and otherwise leaves those two variants out as `StorageLimit`). `play compute-census <player data directory>` builds every variant as a compute program on that device and prints the counts and the causes: all 76 of the Old World player's variants build on llvmpipe and on the AMD Radeon 780M, with none left out; with the default limit of four, 74 build and the two with five storage images are refused. The binding is the first mip level of the texture. A dispatch's writes are in the texture for every later camera render, blit, copy and pixel read, because the host records the dispatch into the same submission, after the operations before it and before the copy a pixel read wants, and wgpu orders the passes of a submission. `tests/storage.rs` (in `offscreen/tests`) writes a pattern from a kernel into an RGBA8 render texture and reads it with a pixel read and, after a blit, from the blit's target; the expected floats come from the kernel's formula. The flush test above reads its kernel through this path, from a serialized compute shader object it writes into a temporary data directory.

The world's record of a render texture states its dimension (2D, 3D, cube, 2D array or cube array) and its volume depth (the slices of a 3D texture, the layers of an array, six faces for each cube of a cube array, 1 for a 2D texture or a cube), and the host makes the texture with that shape the first time a frame names it, before any kernel touches it. A record maps to render-program's `RenderDimension`: `D2`, `D2Array(layers)`, `D3(depth)`, `Cube` (six layers, square) and `CubeArray(cubes)`. A dimension code the world does not define is carried as `Unknown(code)` and the state refuses it as `rendertexture:UnknownDimension`, which leaves out that texture and the records that name it. The depth limit is the device's (`DepthLimit`). A kernel's binding must match the record: a storage image is bound through a 2D view of a plain texture, a 2D-array view of an array, a cube or a cube array (a storage image has no cube view, so the faces are written as layers) and a 3D view of a volume, and a sampled texture through the view of the record's own dimension (2D, 2D array, 3D, cube, cube array). A mismatch leaves the dispatch out as `dispatch:StorageDimension` or `dispatch:TextureDimension`, and the report's example for that cause and the dispatch trace's `reason` say both shapes (`the kernel declares a D2Array view and the render texture is D2`). A 3D texture has one mip and no depth buffer, only kernels read and write it, a record that names one (a blit, copy or camera render) is refused as `VolumeInGraph`, and a pixel read answers its first slice; a kernel samples any layer or slice through a sampled `texture_2d_array` or `texture_3d`. A cube is sampled by a draw, such as a blit, through a cube view. `tests/volumes.rs` writes every layer of an array and every slice of a 3D texture from a kernel and reads each back through a second kernel and a pixel read, with the expected values from the formula the kernel writes. `tests/shapes.rs` checks that each record shape is made with its layers before any kernel touches it (including a one-layer array and a 3D texture of depth 8, written in every slice), that a kernel writes the six faces of a cube through an array view and a blit samples one face through a cube view, that a kernel whose view differs from the record is left out by name with both shapes, and that an unknown dimension code is refused. The report records, for each dispatch, the `GraphicsFormat` code of each render texture it names with what the kernel declares at that binding (`render texture format C bound as storage image F D`, `render texture format C sampled as K D`), even when the host cannot make that texture, so a code the format table lacks can be mapped from the formats it is paired with and not from a table; it also counts the formats of the render textures each frame holds and the dispatches that ran. A mesh with no vertices or with no sub-mesh that has an index to draw is skipped without a failure and counted as `mesh with nothing to draw` with its sub-mesh count, topologies and whether it has indices and vertices; a sub-mesh that draws from indices the mesh lacks is the failure `mesh:IndicesMissing`.

`Report` also carries what a run needs to find out why a dispatch read back zeros. Each dispatch leaves a `DispatchTrace`: the shader and kernel, the variant that runs, the group counts and the thread group size the world holds, the numeric values it sets, the textures the kernel declares with what was bound to each (render, asset, global, none or unset, whether the texture is on the GPU, and how many camera renders before the dispatch wrote it, with the draws they recorded and left out), the buffers with their sizes and non-zero words before and after the flush, the outcome (`ran` or the name of the cause it was left out) and whether the buffers were read back. The report also counts camera draws left out for want of a pass by the `LightMode` values the shader's passes have against the ones the camera selects, the partial texture reads by property and pass, and the texture properties that named no texture the frame can read by name and reason. `play shader-census` counts the player's passes by `LightMode`. `Settings::cameras()` is what `PlayerGpu` uses: a camera selects `UniversalForward`, `UniversalForwardOnly`, `SRPDefaultUnlit`, `ForwardBase` and `Always`, and a pass with no `LightMode` counts as `Always`, the last choice, so any selected tagged pass wins over it and a pass tagged with another mode (`DepthOnly`, `SHADOWCASTER`, `UniversalGBuffer` and the rest) is never drawn. The evidence is in the player's data and our runs: 603 of the 664 passes have no `LightMode`, none carries `Always` or `SRPDefaultUnlit`, 147 of 171 shaders have no tagged pass, every shader a camera render met in a 24-frame RomeTurn42 run had one pass without a tag, and in the 7 shaders that mix tagged and untagged passes the tagged ones are depth, shadow, G-buffer and motion-vector passes. A camera draw whose pass samples a texture no layer names is left out and counted by the texture property (`draws without a texture`), and the rest of the camera's draws are kept; before that, one such draw dropped the whole camera render. A texture property a material leaves unset reads the default its shader declares for it when the host supplies that default: `white` (every channel 1) and `black` (colour 0, alpha 1, an assumption), for 2D properties. The Old World player declares `white` for 221 texture properties, `black` for 23, `bump` for 18, `grey` for 12, `linearGrey` for 1 and no default for 43; the colours and colour spaces of `bump`, `grey` and `linearGrey` are not in the player's data, so a draw that reads one is still left out and counted. The properties given a default are listed as `no texture set, the shader's default read`. A stored texture the engine holds no pixels for is counted as `texture:NotStored` the first time a frame names it; one the host already holds unchanged is not. A camera draw whose mesh lacks a vertex channel the pass reads is left out and counted by channel and shader input (`draws without a mesh channel`), as a draw without a texture is, so one such mesh no longer drops its whole camera render.

### The storage budget

The program runtime holds all GPU storage the host makes (stored textures and meshes, render textures, constants and the staging of pixel reads) under one budget. The budget is a total, not a buffer size: it is not tied to the device's `max_buffer_size`, and the runtime reserves its arena in buffers the device can hold (`ProgramRuntime::arena_allocations_within`). wgpu 30 reports no memory size for an adapter, so `storage_budget::choose` picks it, in this order:

1. `PLAY_GPU_STORAGE_MB`, a whole number of MiB. A value that is not a positive number is ignored and the report says so.
2. For a software adapter such as lavapipe, whose textures live in host memory, a quarter of the `MemAvailable` the host reports, no less than 512 MiB and no more than 2 GiB.
3. 512 MiB for any other adapter.

The `[gpu] adapter` report line names the budget and which rule chose it. When an allocation would not fit, the host gives back what the snapshot being mapped does not name, least recently named first: stored meshes, stored textures and render textures. A snapshot names a render texture when a record reads or draws into it, or a property of a material, a renderer or the globals holds it. A render texture given back is made again, empty, by the next frame that names it. The host does this before it builds a frame's render textures, when an upload is refused and before the frame that copies the texture for a pixel read begins, so the staging fits. The report counts what was given back as `given back to make room`, and a pixel read the budget still has no room for as `pixel reads refused: no copy of the texture could be made: over the storage budget`. A stored mesh or texture whose upload the budget still refuses is counted as a failure of that snapshot and is asked for again, whole, by the next snapshot that names it, so it is uploaded once room exists even though the engine stores no newer generation of it. One the host cannot upload for its own sake (a mesh with no position channel, a texture whose bytes are shorter than its base level, a format the host does not decode) is counted once and not read again until the engine stores a new generation. In both cases the storage of the generation it replaced is given back, so a failed replacement leaves neither old geometry nor old texels to draw from; `tests/mesh_cache.rs` and `tests/texture_cache.rs` (in `offscreen/tests`) hold these claims.

### Wiring a frame

`PlayerGpu` (in `gpu_player.rs`) owns a device, the `OffscreenHost` on it and the counts of a run. `run_player` makes one when the machine has an adapter (`--gpu-work off` skips it), registers its flush handler with `DisunityHost::set_gpu_flush` before the scene loads, and after each advance calls `PlayerGpu::frame`, which takes `graphics_snapshot()`. A frame whose snapshot holds no work returns at once and leaves the device alone, so the run is the one it was before. With work, the records are adapted, built, admitted against a frame of the authority, encoded, submitted and waited for; the counts of records, dispatches, skips and failures print at the end as `[gpu]` lines.

The flush handler reads meshes, textures and samplers through `GpuFlush` (`mesh_channels_since`, `player_texture` and `texture_sampler`), as `PlayerGpu::frame` reads them through `DisunityHost`, so a mesh or texture the first flush names is read for that flush. `tests` in `gpu_flush_tests.rs` runs a managed fixture whose flush reads a stored texture, its sampler and a stored mesh with no frame before it.

The windowed paths do not run the offscreen work yet. `SceneGpu::admit_offscreen` takes the operations before the scene is encoded, but the viewer makes the device, its submission authority and the renderer's allocation reservation for the program arena, and the retained and live drivers have no hook that gives them to the player. That hook is the remaining step of the live wiring.

`play_player_window` draws built-player mesh objects and screen-space overlay UI
through the retained scene renderer. Text coverage and image quads retain native
hierarchy order and pixel clip bounds. UI replacements track draw changes, image
texture generations and viewport size; unchanged frames reuse the overlay.
An image whose identity has no available sprite texture is left out of the UI
frame. The driver names each unavailable identity once on stderr as
`UI image <id> is left out: <reason>`: a missing scene texture, an identity the
managed host has not stored, or a texture conversion failure. A texture stored
later becomes visible without changing the UI draw. Other images, text and 3D
objects continue to draw; missing text coverage remains an error. The renderer's
explicit-texture overlay API still rejects unresolved identities.
Ordinary 2D scene quads and world-space UI remain outside this retained path.

The window opens at a fixed default view and moves to the game's camera on the first frame
that shows mesh objects and presents a perspective camera; from then on the mouse navigation
moves it. While frames with objects present no camera, or one the viewer cannot draw (an
orthographic one, for example), the window keeps its view and tries again on the next such
frame, and the driver names each reason once on stderr.

### Lighting the retained scene

The retained scene is lit by the World's main light, chosen in `scene_light.rs`. These are the
engine's choices:

- The main light is the first directional light the prepared frame lists, in component order.
  `RenderSettings.sun` and the ambient settings live only in managed memory and are not read.
  Without a directional light the scene stays unlit, as before.
- The scene sun shines back along the light's forward axis. Its irradiance is the light's
  intensity, at most 10. The scene sun has no colour, so the light's colour is not used.
- The ambient light is white, 0.3 from above and 0.15 from below. The scene asks for no
  atmosphere, so the game's clear colour stays the background.
- Shadows exist only when the first frame's main light casts them, because the viewer chooses
  its shadow resources when it starts. They use three cascades split 10 m, 40 m and 150 m from
  the camera, a 2048-texel map, a depth bias of 0.0005 and a normal bias of 2 cm. The light's
  own bias values are not used, since the engine defines no unit for them. A light that starts
  casting shadows later lights the scene without them.
- Each frame sends new scene effects only when its lighting changed. After a frame has been
  lit, a frame without a directional light keeps the last sun's direction with no irradiance.
- The presented camera's `renderShadows` turns those shadows on and off: each frame publishes
  the camera with the matching shadow policy when the setting changed, at the last accepted
  pose when the camera did not move. Until the game's camera is shown that pose is the one the
  window opens with, so the setting applies even when the game presents no camera. A camera
  without camera data keeps the published policy. A viewer
  that started without shadows ignores the setting, since it cannot add shadow resources.

## Tests

The library's synthetic retained-player UI test runs the managed host and captures
windowless frames. It requires .NET 8 and a GPU adapter and checks image bytes,
text, clipping and unchanged-frame UI update counts without opening a window.

`scene_light` unit tests pin the main-light choice, the sun direction of a turned light, the
irradiance limit, the fixed shadow settings, when a frame sends new effects, which shadow
policy a camera's `renderShadows` publishes and, through sequences of frames, the pose it is
published at, from the window's opening pose, and that a camera the viewer refuses is sent
again. `camera_start` unit tests pin when the window starts at a game camera that appears late or
after a refused one, and that each reason it waits is reported once.
`scene_tables::tests::lit` starts the viewer as `play_player_window` does and checks on a GPU
adapter that a shadow-casting sun draws into the shadow cascades, that no sun, or a sun
without shadows, draws none, and that a camera with `renderShadows` off stops the started
shadows from drawing.

`tests/play_window.rs` plays all three games in a 480x270 window and checks the captured pixels. It needs an X display; run it as the lavapipe CI job does:

```sh
env -u WAYLAND_DISPLAY xvfb-run --auto-servernum cargo test -p worldrunner-play --test play_window
```

The test starts each game in a child process without `WAYLAND_DISPLAY` itself. Do the same for the `play` command under `xvfb-run`: with a Wayland session in the environment the window opens there instead, and a window the compositor never shows is never presented.

The offscreen adapter's tests build synthetic worlds and serialized files and need no game data. The GPU tests run a camera render, a blit of every pass and a copy through the adapter and render-program on a real adapter and compare predicted pixels; run them on lavapipe with:

```sh
VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.json WGPU_BACKEND=vulkan cargo test -p worldrunner-play --lib offscreen -- --test-threads=1
```

`tests/draw_mesh.rs` (in `offscreen/tests`) binds and clears a render texture and draws synthetic meshes with `DrawMesh` through the flush, with a shader that places its vertices by `unity_ObjectToWorld` and `unity_MatrixVP`: a quad over the left half of clip space under an identity view and projection, the same quad moved by the object matrix, an orthographic 0 to 1 projection, sub-mesh 1 of a two-sub-mesh mesh, and a two-pass shader whose second pass blends over the first. Each test predicts the 8-bit texels from the matrices, colours and blend factors. MeshUnavailable, EmptyMesh, NoSuchSubmesh, NoSuchPass and UnboundTarget are checked by name. Reclamation tests also check that a mesh named only by DrawMesh stays resident, that eviction removes its metadata, and that a later draw reloads it.
