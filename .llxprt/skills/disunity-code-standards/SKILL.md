# real-disunity code standards

## Architecture

- Separation of concerns: each crate and module owns one responsibility. The native runtime owns world state, the FFI exposes it, the managed bridge adapts Unity APIs, the renderer renders, the player composes them.
- Inversion of control: depend on traits and injected services, not concrete singletons or globals. Configuration is passed in explicitly, not read from ad hoc environment variables deep in library code.
- DRY: one implementation per concept. Extract shared helpers instead of copying logic between tests, crates or games.
- Extensibility: new games, providers or render stages plug in through the existing extension points (frame executor stages, provider registration, capability negotiation) without editing unrelated code.
- Respect the layer rules enforced by `cargo xtask policy` and `crates/xtask/src/layers.rs`.

## Limits (enforced, never loosened)

- Functions: at most 60 lines, 6 arguments, cognitive complexity 15.
- Type complexity 250; at most 3 bool fields per struct.
- Source files: aim for under 750 lines, hard limit 1000. If a file approaches the limit, split it by responsibility. Never raise a limit, add an `allow`, or add an exception to make code pass.
- Warnings are errors. No lint suppressions.

## Change discipline

- When behavior changes or a bug is fixed, change it everywhere to the new way. Do not keep the old path alongside the new one. No `legacy_`, `v1`/`v2` twins, "historical preservation" modes, or flags that select the broken behavior.
- No backward-compatibility shims for internal APIs. Update every caller.
- Delete dead code, unused generated tables and obsolete tests instead of leaving them.
- Tests assert real behavior. Do not weaken an assertion, widen a tolerance, add a retry, or mark a test ignored to make it pass. Fix the code or the test setup.
- Generated code is regenerated by committed tooling and is not used to fingerprint the repository.
